Technical Specification: Agentic AI System for Medical Device Premarket Review Infographic Generation (WOW UI)
1. Executive Summary
This document serves as the comprehensive technical specification for the Agentic AI System for Medical Device Premarket Review Infographic Generation. Designed with a "WOW UI" philosophy, this application is a next-generation, multimodal, and multilingual AI platform tailored specifically for medical device professionals, regulatory affairs specialists, and compliance officers.
The system allows users to input raw, unstructured medical device premarket review guidance, 510(k) summaries, or regulatory notes. Utilizing advanced Large Language Models (LLMs) via the Gemini API, the system restructures the input into organized markdown, extracts up to 30 critical regulatory topics, generates detailed code-driven infographic specifications for each topic, and compiles a comprehensive compliance review checklist.
The user interface is designed to be visually stunning and highly interactive, featuring real-time theming with Light/Dark modes, bilingual support (English, Traditional Chinese, or Dual), and 20 unique visual styles inspired by famous painters. This specification details the system architecture, component hierarchy, state management, AI integration strategies, data models, and deployment considerations.
2. System Architecture Overview
The application is built as a Single Page Application (SPA) using a modern, high-performance frontend stack. It relies heavily on client-side processing for UI state management while offloading heavy natural language processing and data extraction tasks to the Gemini API.
2.1. Technology Stack
Core Framework: React 19 (Functional Components & Hooks)
Build Tool: Vite 6.x
Language: TypeScript (Strict Mode)
Styling: Tailwind CSS v4 (Utility-first CSS)
Animations: Framer Motion (Declarative animations and transitions)
Icons: Lucide React (Consistent, scalable SVG iconography)
Markdown Rendering: React-Markdown
AI Integration: @google/genai SDK (Gemini 3.1 Pro Preview)
Utility Libraries: clsx and tailwind-merge for dynamic class name composition.
2.2. Architectural Pattern
The system follows a Container-Presenter pattern combined with a Monolithic State Object approach at the root level.
App.tsx acts as the primary state container and theme orchestrator.
Child components (Sidebar, Dashboard, InputPanel, OutputPanel) act as presenters that receive state and state-mutating functions via props.
External services (geminiService.ts) encapsulate all asynchronous API calls, keeping the UI components pure and focused on rendering.

4. Theming Engine and "WOW UI" Aesthetics
The "WOW UI" is driven by a dynamic theming engine that manipulates CSS Custom Properties (variables) at the :root level. This allows for instantaneous, application-wide visual updates without requiring component re-renders.
4.1. Light and Dark Mode
The application supports a standard Light/Dark mode toggle. This is implemented by adding or removing the .dark class on the <html> element, which Tailwind CSS uses to apply dark: variant utility classes. Furthermore, base background and text colors are injected as CSS variables:
--bg-primary: The main background color (White in light mode, Slate-900 in dark mode).
--bg-secondary: The secondary background for sidebars and panels (Slate-50 in light mode, Slate-800 in dark mode).
--text-primary: High-contrast text color.
--text-secondary: Muted text color for subtitles and metadata.
4.2. Painter-Inspired Styles
To fulfill the requirement of 20 styles based on famous painters, the system includes a predefined array of color palettes in src/styles/themes.ts. Each style defines a primary, secondary, accent, background, and text color.
When a user selects a style (or clicks the "Jackpot" randomizer button), the App.tsx useEffect hook injects these colors into the DOM:
code
JavaScript
root.style.setProperty('--color-primary', style.colors.primary);
root.style.setProperty('--color-secondary', style.colors.secondary);
root.style.setProperty('--color-accent', style.colors.accent);
These variables are then consumed by Tailwind utility classes via inline styles (e.g., style={{ backgroundColor: 'var(--color-primary)' }}) or custom CSS layers.

6. AI Integration & Agentic Workflow
The core intelligence of the application is powered by the @google/genai SDK, specifically utilizing the gemini-3.1-pro-preview model. This model was selected for its advanced reasoning capabilities, large context window (crucial for long regulatory documents), and strict adherence to JSON schema outputs.
All AI interactions are encapsulated within src/services/geminiService.ts.
6.1. Prompt Engineering and Structured Outputs
To ensure the UI receives predictable, renderable data, the system heavily utilizes Gemini's responseSchema configuration. This forces the LLM to output valid JSON that exactly matches the TypeScript interfaces.
Agent 1: Markdown Transformer (transformToMarkdown)
Purpose: Cleans messy, unstructured notes, OCR artifacts, or pasted PDFs into clean markdown.
Prompt Strategy: Instructs the model to create section headings, numbered lists, and tables.
Output: Plain text (Markdown).
Agent 2: Topic Extractor (extractTopics)
Purpose: Implements the core of the infographic-code-factory-30 skill. Extracts exactly 30 regulatory topics.
Prompt Strategy: Instructs the model to extract topics, provide bilingual summaries, list "why it matters", and assign confidence scores.
Schema Enforcement: Uses Type.ARRAY of Type.OBJECT with strictly required properties (topic_id, title_en, title_zh, etc.).
Resilience: Wraps the JSON.parse in a try/catch block to prevent application crashes if the LLM hallucinates malformed JSON.
Agent 3: Infographic Planner (generateInfographicSpecs)
Purpose: Maps extracted topics to visual templates and generates the copy deck.
Prompt Strategy: Takes the previously extracted topics as context. Instructs the model to define narrative goals, select templates (timeline, flowchart, etc.), and extract key takeaways and evidence anchors.
Batching Consideration: In a full production environment, generating 30 complex JSON objects in a single prompt might hit output token limits. The current implementation processes a subset (slice) for prototype speed, but the architecture supports full 30-item generation.
Agent 4: Checklist Generator (generateChecklist)
Purpose: Scans the document to build a compliance review checklist.
Prompt Strategy: Instructs the model to generate actionable review items with source anchors.
Schema Enforcement: Ensures each item has an id, description, status, and anchors.
6.2. Error Handling and Edge Case Mitigation
AI outputs are inherently non-deterministic. The system implements several layers of defense against malformed or incomplete data:
JSON Parsing Safety: All API responses are parsed within try/catch blocks. If parsing fails, an empty array [] is returned, preventing fatal React rendering errors.
Optional Chaining & Fallbacks: During rendering, the UI assumes that any nested property or array might be undefined.
Example: {(spec.template || 'Template').toUpperCase()} prevents TypeError: Cannot read properties of undefined.
Example: {(topic.tags || []).map(...)} prevents mapping over undefined arrays.
UI State Feedback: The isProcessing boolean disables action buttons during API calls to prevent race conditions and duplicate requests. The statusMessage provides transparent feedback to the user regarding the current agentic step.
7. Document Processing Pipeline
The workflow follows a strict, sequential agentic pipeline, ensuring that each step builds upon the context established by the previous step.
Ingestion: User pastes raw text or drops a file. The FileReader API reads the content into state.inputContent.
Structuring (Agent 1): The raw text is sent to Gemini to be formatted into Markdown. This normalizes the data, making it easier for subsequent agents to parse headings and bullet points.
Extraction (Agent 2): The structured markdown is analyzed to extract 30 distinct topics. The system requests bilingual outputs simultaneously, ensuring semantic parity between English and Traditional Chinese.
Specification (Agent 3): For the extracted topics, the system generates Infographic Specs. This step transforms abstract concepts into concrete visual blueprints (e.g., deciding that a regulatory transition period should be a "timeline" template).
Verification (Agent 4): A checklist is generated to ensure all compliance requirements mentioned in the text are accounted for.
8. Bilingual Support Architecture
The application is designed from the ground up to support global regulatory teams, specifically focusing on English and Traditional Chinese (繁體中文).
UI Localization: The Language state (en, zh, dual) dictates how data is rendered.
Data Model Design: Instead of relying on real-time translation during rendering, the AI is instructed to generate bilingual fields upfront (e.g., title_en and title_zh).
Rendering Logic:
If state.language === 'en', only title_en is shown.
If state.language === 'zh', only title_zh is shown.
If state.language === 'dual', title_en is shown as the primary header, with title_zh rendered directly below it in a muted, secondary style. This is crucial for regulatory contexts where precise terminology in both languages must be compared.
9. Security, Privacy, and Compliance Considerations
Given the sensitive nature of medical device premarket reviews (e.g., unreleased 510(k) data, proprietary algorithms, clinical trial results), security is paramount.
9.1. API Key Management
In this prototype, the Gemini API key is injected via Vite's define configuration (process.env.GEMINI_API_KEY).
Production Warning: In a true production environment, exposing the API key to the client-side bundle is a severe security risk. The architecture must be migrated to a Full-Stack model (e.g., Next.js or Express + Vite) where API calls are proxied through a secure backend server.
9.2. Data Privacy
Currently, all document processing happens via API calls to Google's Gemini models. Users must be informed of the data sharing policies of the underlying LLM provider.
For highly confidential regulatory documents, the system should be configurable to use enterprise-grade, zero-data-retention API endpoints, or self-hosted open-source models (via Hugging Face endpoints).
10. Future Scalability and Deployment
While currently built as a client-side SPA prototype suitable for Hugging Face Spaces or static hosting, the architecture is designed to scale.
10.1. Backend Migration
To support user authentication, document saving, and secure API key management, the system should be migrated to a Node.js/Express backend. The geminiService.ts functions would become REST or GraphQL endpoints.
10.2. Actual Infographic Rendering
Currently, the system generates the specifications for infographics. The next architectural phase involves integrating a charting library (e.g., D3.js, Recharts, or Apache ECharts). A new component, <InfographicRenderer spec={spec} />, would dynamically select the correct chart component based on spec.template and map spec.data_schema to the chart's required data format.
10.3. Export Capabilities
Future iterations will require the ability to export the generated Webpage Bundle Plan. This involves generating a .zip file containing the index.html, styles.css, and infographics.json files, allowing regulatory teams to host the interactive infographics on their internal intranets or submit them alongside FDA documentation.
